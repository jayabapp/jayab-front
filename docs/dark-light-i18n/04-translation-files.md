# فیچر ۰۴ — ترجمهٔ مرحله‌ای، ICU و پیام‌های خارج از React

مبنا: `feat/new-app@c8e26fff` · وابسته به ۰۳ · خروجی: ترجمهٔ رابط با کلیدهای تایپ‌شده.

## وضعیت واقعی

در app/components/features تعداد ۲۶۰ فایل LocalStrings را import می‌کنند. اسکن حروف Arabic-script در ۹۵ فایل فقط **کاندید** متن است: comment، regex، نام بومی زبان و محتوای عمدی هم شمرده می‌شوند. عددهای این دو گروه با هم جمع نمی‌شوند؛ هم‌پوشانی دارند.

متن UI علاوه بر JSX در feature mapperها، schemaهای Yup، helper فرمت، notify و `api_services/common/apicall.helper.ts` است. `PropertyDetailsContent.tsx` tab/breadcrumb را از _STRINGS می‌سازد؛ مهاجرت آن فقط ترجمهٔ leafها نیست.

## وضعیت پیاده‌سازی

**ابزار.** `yarn i18n:check` (parser مستقیم `@formatjs/icu-messageformat-parser@3.5.19`): JSON معتبر، رشتهٔ non-empty، برابری leaf keyها با fa، ICU معتبر با `other`، selectorهای plural مجاز همان زبان، برابری نام/نوع آرگومان‌ها و tag از allowlist (`b i em strong br link`). `yarn i18n:namespaces` گراف import هر entry اپ را می‌خواند، namespaceهای مصرف‌شده در فایل‌های کلاینت را حساب می‌کند و اگر `ROOT_NAMESPACES` در `app/layout.tsx` یا `<IntlNamespaces namespaces={[…]}>` همان page کم داشته باشد شکست می‌خورد؛ همچنین هر رشتهٔ شبیه کلید (`ns.key`) که در `messages/fa.json` نباشد را گزارش می‌کند (برای helperهایی که translator شل می‌گیرند و TypeScript کلیدشان را نمی‌سنجد).

**مهاجرت.** همهٔ مصرف‌های `_STRINGS` و متن‌های فارسی خودبسندهٔ کامپوننت‌ها منتقل شد (۹۴۹ پیام × سه زبان؛ مقدار fa هر کلید با مقدار اصلی `_STRINGS` یکی است): جستجو و شهر، فهرست و جزئیات آگهی، فیلترها و مرتب‌سازی، رزرو و تماس، چت، احراز هویت و OTP، پروفایل و پشتیبانی، مالک و بهبود تصویر، مشاور، محتوا/بلاگ/FAQ، فرم‌ها و مودال‌ها، toastها، aria-label/alt/title و منوی پروفایل. `utils/LocalStrings.ts` فقط سه کلید metadata صفحهٔ `/rooms` را نگه می‌دارد (metadata فارسی می‌ماند). ۱۱۶ کلید بی‌مصرف و کدهای مرده (`formatCompactToman`، `MinuteToHour`، `ReserveReqTypes`، `menuDropDownItems`، `simpleWeekDays`، `ShareButton`) حذف شدند.

**الگوها.** کامپوننت async از `getTranslations`، بقیه از `useTranslations`. helperهای خالص translator یا واژه‌ها را صریح می‌گیرند (`createPropertySteps(id, t)`، `buildLocationLabel(entries, words)`، `contactPrefillValues`)؛ `useFormatToman` و `useListSeparator` نسخهٔ hook هستند. اسکیماهای Yup و `apiCall` پیام را به‌صورت کلید می‌دارند و `YupValidator`/`handleError` با `lib/i18n/browser-translator.ts` ترجمه می‌کنند (provider ریشه translator را یک‌بار می‌سپارد؛ فقط namespaceهای ریشه مثل `common/auth/errors` از این مسیر ترجمه می‌شوند). عبارت‌های «عدد + اسم» ICU plural شدند تا عربی (zero/one/two/few/many) و انگلیسی درست جمع بسته شوند؛ fa از `other` با `{count}` خام استفاده می‌کند تا رقم‌ها دست‌نخورده بمانند. provider صفحه با `<IntlNamespaces>` به provider ریشه merge می‌شود (برخلاف nested ساده، namespaceهای والد گم نمی‌شوند).

**عمداً بیرون این فاز.** متن‌های وابسته به API/CMS و محتوای فارسی backend (عنوان آگهی، قوانین/توضیحات، `messages.fa`، مقایسهٔ `includes("نیست")`)، metadata/JSON-LD، پیام‌های route handlerهای سرور، نام ماه/روز جلالی و `moment.loadPersian` و `daysOfOurLives` (منطق تقویم)، ارقام و واژهٔ‌های `Num2Persian`/`timeLeft`/`numberWithCommas`، جداکنندهٔ `search-option-draft`، فرمت تاریخ `dddd، jD jMMMM`، ابزار داخلی `TestAccessManager`، صفحهٔ `qa-login` و ویجت محصول داخل HTML-CMS (`convertHTMLtoReact`) — گروه فرمت‌دهی فیچر ۰۹ یا محتوای backend‌اند. ترجمهٔ عربی و انگلیسی (به‌ویژه عبارت‌های مالی/رزرو/حقوقی) بازبینی انسانی ندارد؛ تا آن زمان و تا پایان فیچر ۰۸ (RTL/LTR) `NEXT_PUBLIC_ENABLED_LOCALES` باید `fa` بماند.

## قرارداد پیام

### تکمیل محتوای سه‌زبانهٔ صفحهٔ اصلی

در ادامهٔ فاز UI، `homeContent` نیز به CMS سه‌زبانه متصل شد. فارسی در ستون‌های اصلی حفظ می‌شود؛ `Content.translations` نسخه‌های مستقل `ar` و `en` را با `title`، `small_text`، `full_text`، `html` و `seo.{metaTitle,metaDescription}` نگه می‌دارد. canonical و تنظیمات sitemap در رکورد اصلی مشترک‌اند. پنل در ایجاد/ویرایش رکورد با کلید `homeContent` بخش‌های عربی و انگلیسی دارد؛ ذخیرهٔ فوری تغییرات ویرایشگر از جاافتادن آخرین تغییر متن هنگام ذخیره جلوگیری می‌کند. ارسال‌نکردن `translations` از پنل قدیمی ترجمه‌ها را حذف نمی‌کند؛ ارسال `{}` حذف صریح آن‌هاست.

قرارداد خواندن: `GET /contents/by-key/homeContent?locale=fa|ar|en`؛ زبان نامعتبر ۴۲۲، نبود پارامتر = فارسی. پاسخ `content_locale` را گزارش می‌کند و نسخه‌های دیگر را serialize نمی‌کند. ترجمه باید یک نسخهٔ کامل باشد تا متن/سئوی فارسی با آن ترکیب نشود. CacheInterceptor بک بر اساس URL شامل query، fetch سرور با locale در URL، React cache با آرگومان locale، و query key کلاینت با locale جدا می‌شوند. تغییر زبان همان reload قرارداد فعلی را دارد. HTML ترجمه نیز از مسیر `HTMLGenerator` و sanitizer موجود عبور می‌کند.

صفحه و metadata از یک resolver مشترک استفاده می‌کنند؛ عنوان، توضیحات و Open Graph صفحهٔ اصلی با زبان هماهنگ‌اند. اگر API قدیمی باشد یا نسخهٔ زبان موجود نباشد، شعار و عنوان از پیام‌های سه‌زبانه می‌آیند و مقالهٔ فارسی زیر عنوان انگلیسی/عربی نمایش داده نمی‌شود. این fallback جای ترجمهٔ CMS را نمی‌گیرد. سایر محتوای backend و JSON-LD همچنان خارج از این تغییرند.

ترتیب انتشار: ابتدا migration بک `20261011090000_add_content_translations` با `prisma migrate deploy` و سپس build/restart بک؛ بعد پنل و فرانت. migration فقط ستون JSONB را اضافه و ترجمهٔ اولیهٔ متن فعلی صفحهٔ اصلی را برای همان کلید درج می‌کند؛ فیلدهای فارسی، دیگر محتوا و تنظیمات SEO را تغییر نمی‌دهد. migration روی دیتابیس این نشست اجرا نشده است. کش CMS فرانت ۶۰۰ ثانیه و کش پاسخ بک ۱۸۰ ثانیه است؛ ویرایش محتوا ممکن است تا پایان این بازه‌ها دیده نشود. revalidation عمومی فعلی نیازمند مجوز ادمین است.

تست‌ها: serializer و نسخه‌های اولیهٔ migration، validation تو‌در‌توی DTO، حفظ ترجمه در ویرایش پنل قدیمی، GET زبان و جداسازی واقعی cache با Nest/Supertest؛ fallback فرانت در `features/home/mappers/home-content.mapper.test.ts`.

### آیتم‌های سه‌زبانهٔ بخش‌های صفحهٔ اصلی

عنوان بخش‌های «انواع اقامتگاه‌ها»، «شهرهای پربازدید» و «جستجوی سریع» از پیام‌های `common.propertyType`، `content.mostVisitedCities` و `footer.quickSearch` می‌آید. متن آیتم‌ها از پنل است: انواع اقامتگاه‌ها از `PropertyOption` با گروه `PROPERTY_TYPE`، و شهرها/جستجوی سریع از `LandingPage` با positionهای `popular_city` و `quick_search`.

در پنل «آپشن‌های املاک ← ویرایش گزینهٔ گروه نوع اقامتگاه» (`/property-options`) و «صفحات لندینگ ← ویرایش» (`/landing-pages`) بخش «ترجمه عنوان نمایشی» دارد. عنوان اصلی فارسی باقی می‌ماند؛ فیلدهای عربی و انگلیسی مستقل‌اند. خالی کردن فیلد و ذخیره، نسخهٔ همان زبان را حذف می‌کند. نبود ترجمه در API به عنوان فارسی برمی‌گردد؛ `title_locale` زبان واقعی عنوان را مشخص می‌کند. ویرایش از پنل قدیمی و PATCH جدول، ترجمه‌های قبلی را حفظ می‌کند.

APIهای `/user/property-options?group[]=PROPERTY_TYPE&locale=en` و `/user/landing-pages?placement=home&locale=ar` زبان اختیاری fa/ar/en دارند و نقشهٔ ترجمه‌ها را در پاسخ عمومی منتشر نمی‌کنند. فرانت locale را در دریافت سرور، hydration و query key جستجوی مقاصد محبوب قرار می‌دهد. آدرس، شناسه، ترتیب و فیلترها مستقل از زبان می‌مانند. «جستجوی سریع» فوتر منبع جداگانهٔ `footer-quick-search-links` دارد و جزو آیتم‌های این بخش صفحهٔ اصلی نیست.

migration `20261012090000_add_home_section_title_translations` ستون JSONB به `property_options` و `landing_pages` اضافه می‌کند و ترجمهٔ اولیهٔ ۸ نوع اقامتگاه، ۲۸ شهر و ۸ جستجوی سریع دامنهٔ بررسی‌شده در ۲۰۲۶/۱۰/۱۲ را درج می‌کند. درج فقط روی شناسه/آدرس و عنوان فارسی منطبق انجام می‌شود؛ نسخه‌های موجود ادمین مقدم‌اند. موارد جدید یا تغییرنام‌یافته از پنل تکمیل می‌شوند. پیش از انتشار بک، `prisma migrate deploy` لازم است؛ migration در این نشست روی دیتابیس اجرا نشده است.

### عنوان کارت اقامتگاه، کارت شهر و موقعیت سه‌زبانه

عنوان کارت اقامتگاه از `Property.title` می‌آید. موقعیت عمومی کارت از عنوان رکوردهای مرتبط `City` (شهر و محله، یا استان) ساخته می‌شود؛ این متن، `Property.address` نیست. عنوان کارت شهرهای لندینگ از `LandingPage.title` می‌آید و از ویرایشگر لندینگ در پنل قابل تغییر است. برای نام شهر/استان/محله در کارت اقامتگاه، در بخش «شهرها» پنل رکورد همان موقعیت را ویرایش کنید؛ فیلدهای عربی و انگلیسی در فرم ایجاد و ویرایش اضافه شده‌اند.

عنوان و آدرس اصلی ملک فارسی می‌مانند. در مرحلهٔ اطلاعات اولیهٔ ویرایش اقامتگاه، بخش «ترجمه عنوان و آدرس اقامتگاه» دو فیلد مستقل عنوان و آدرس برای هر زبان عربی و انگلیسی دارد. همین فرم از مسیر ویرایش اقامتگاه پنل با `AdminSsoFrame` باز می‌شود؛ بنابراین ادمین نیز از همان فرم ترجمه‌ها را مدیریت می‌کند. محدودیت ویرایش عنوان برای میزبان با وضعیت‌های قبلی حفظ شده است. خالی کردن یک فیلد، ترجمهٔ همان فیلد را حذف می‌کند؛ عنوان و آدرس مستقل به فارسی برمی‌گردند. درخواست قدیمی که `translations` ندارد، ترجمه‌های ذخیره‌شده را حذف نمی‌کند؛ `{}` صریح همهٔ نسخه‌ها را پاک می‌کند. ترجمهٔ runtime یا بازنویسی خودکار متن میزبان انجام نمی‌شود.

API فهرست، جزئیات، مشابه‌ها و علاقه‌مندی‌های اقامتگاه `locale=fa|ar|en` دریافت می‌کند. serializer فقط متن نسخهٔ انتخاب‌شده و زبان واقعی هر فیلد (`text_locales`) را برمی‌گرداند. شناسه، slug، مسیر لینک، قیمت، ترتیب و فیلتر جغرافیایی از ترجمه تأثیر نمی‌گیرند. آدرس دقیق ترجمه‌شده نیز فقط تحت شرط قبلی `is_location_visible || isOwner` منتشر می‌شود؛ نقشهٔ ترجمه‌ها در پاسخ عمومی وجود ندارد. در API شهرها نیز نسخهٔ انتخاب‌شده و `title_locale` برای هر سطح درخت برمی‌گردد. جستجوی متن آزاد شهرها همچنان از عنوان اصلی فارسی استفاده می‌کند.

فرانت زبان را در دریافت سرور و مرورگر و کلیدهای کش فهرست/جزئیات/مشابه‌ها/علاقه‌مندی‌ها قرار می‌دهد. هنگام تعویض زبان، placeholder فهرست از زبان قبلی نمایش داده نمی‌شود. عنوان و موقعیت کارت‌ها با `lang` و `bdi/dir=auto` از متن فارسی جایگزین یا ترکیب زبان‌ها پشتیبانی می‌کنند.

migration `20261012100000_add_property_and_city_translations` ستون JSONB به `cities` و `properties` اضافه می‌کند. ترجمهٔ اولیه برای ۳۱ نام استان و ۹ موقعیت بررسی‌شده، نام شهرهای محبوب migration قبلی، و ۱۲ عنوان اقامتگاه صفحهٔ اصلی در تاریخ ۲۰۲۶/۱۰/۱۲ آماده شده است. عنوان ملک فقط با تطبیق شناسه، کد و متن اصلی درج می‌شود؛ ترجمه‌های موجود مقدم‌اند. این کار تمام آگهی‌های موجود را ترجمه نمی‌کند؛ بقیهٔ عنوان‌ها و آدرس‌ها باید از فرم ویرایش تکمیل شوند و تا آن زمان متن فارسی نمایش داده می‌شود. آدرس خصوصی در backfill درج نشده است.

ترتیب انتشار: اجرای migrationهای بک با `prisma migrate deploy`، تولید Prisma Client و build/restart بک، سپس انتشار پنل و فرانت. migration در این نشست روی دیتابیس اجرا نشده است. تست‌های serializer، حریم خصوصی، اعتبارسنجی ترجمه، ذخیره/حذف نسخه‌ها و API واقعی Nest با کش زبان‌ها، همراه تست mapper فرم فرانت، این قرارداد را پوشش می‌دهند.

### قوانین سه‌زبانه و چیدمان ورود

قوانین مودال `/auth` از رکورد `terms` در CMS می‌آید؛ رکورد بررسی‌شده در دامنه شناسهٔ ۱۱ دارد. پنل در «محتوای پایه ← محتوای پایه ← ویرایش قوانین و مقررات» برای کلید `terms` بخش «ترجمه‌های قوانین و مقررات» دارد. متن فارسی در ویرایشگر اصلی، و متن کامل عربی/انگلیسی در ویرایشگر هر زبان ویرایش می‌شود. عنوان، توضیحات و SEO مستقل‌اند. کامپوننت مشترک `Panel/components/Content/ContentTranslationsEditor.tsx` هم صفحهٔ اصلی و هم قوانین را پوشش می‌دهد؛ برداشتن تیک زبان و ذخیره، ترجمهٔ همان زبان را حذف می‌کند. متن خالی یا markup خالی ویرایشگر برای نسخهٔ قوانین در پنل و بک رد می‌شود؛ serializer نیز چنین نسخه‌ای را منتشر نمی‌کند.

`useCmsContent("terms")` زبان فعال را در query و cache key می‌فرستد؛ درخواست مودال فقط هنگام بازشدن فعال می‌شود. صفحهٔ مستقل `/terms` و metadata آن نیز با resolver سرور locale را ارسال می‌کنند. اگر ترجمه موجود نباشد یا API قدیمی باشد، اصل فارسی با `lang="fa"`، `dir="rtl"` و پیام توضیحی به زبان انتخاب‌شده باقی می‌ماند. متن حقوقی پنهان یا با ترجمهٔ ساختگی جایگزین نمی‌شود. HTML مودال نیز مانند صفحهٔ مستقل از `sanitizeCmsHtml` عبور می‌کند.

migration جدید `20261012060000_add_terms_translations` پس از migration ستون translations اجرا می‌شود. ترجمه‌های اولیهٔ عربی و انگلیسی شش بخش و ۵۶ بند متن دامنهٔ بررسی‌شده در ۲۰۲۶/۱۰/۱۲ را پوشش می‌دهند. برای جلوگیری از درج ترجمهٔ قدیمی روی قوانین تغییرکرده، backfill فقط وقتی SHA-256 متن اصلی برابر `4e062f46d10fecab49220734c6e92c1a0a85c2641e5138550a7d38c899b0d8a0` باشد انجام می‌شود. نسخه‌های قبلی ویرایش‌شدهٔ ادمین مقدم‌اند؛ متن فارسی و دیگر رکوردها دست‌نخورده می‌مانند. در صورت تفاوت متن اصلی، ترجمه‌ها باید برای همان متن از پنل تکمیل شوند. ترجمهٔ اولیه بازبینی انسانی حقوقی نشده است.

ترتیب انتشار: `prisma migrate deploy` بک، build/restart بک، سپس پنل و فرانت. migration در این نشست روی دیتابیس اجرا نشده است. زمان کش همان محدودیت ۱۸۰ ثانیهٔ بک و ۶۰۰ ثانیهٔ فرانت است.

چیدمان فیزیکی برند در فرم شماره و کد تأیید و موقعیت/جهت فلش `AuthHeader` با wrapper دارای `dir="rtl"` در همهٔ زبان‌ها مطابق حالت فارسی ثابت است؛ عنوان هدر همچنان جهت زبان انتخاب‌شده را دارد. تست مرورگر ایزوله با کامپوننت‌ها، hook خواندن CMS و CSS واقعی (با transport و احراز هویت جایگزین‌شده) در fa/ar/en و عرض‌های ۳۲۰، ۳۹۰، ۷۶۸ و ۱۲۸۰ اجرا شد؛ حالت نبود ترجمه، cache زبان، بازگشت مرحلهٔ OTP و پاک‌سازی HTML نیز بررسی شدند. این پیش‌نمایش، تست نسخهٔ منتشرشدهٔ دامنه نیست.

namespaceها: common، header، theme، language، auth، listing، search، profile، chat، reserve، owner، errors، validation. کلید بر اساس مفهوم باشد: ورود حساب و ساعت ورود یک کلید ندارند. fa منبع key schema است؛ هر سه زبان leaf key برابر، مقدار non-empty و نام/type آرگومان ICU یکسان دارند.

- از ICU parser استفاده شود؛ regex برای parse nesting و plural کافی نیست.
- selectorهای plural بین زبان‌ها الزاماً یکسان نیستند؛ وجود other الزامی است. برای عربی نمونه‌های ۰، ۱، ۲، ۳، ۱۱، ۱۰۰ بررسی شوند. فارسی نیز طبق Intl.PluralRules رفتار one/other دارد؛ برای جمله‌های دارای متن یکسان می‌توان فقط other نوشت.
- ترجمهٔ rich text فقط با tag allowlist و t.rich باشد؛ HTML خام به dangerouslySetInnerHTML نرود.
- توضیح مترجم در فایل جدا مثل messages/context.json قرار گیرد؛ _context داخل message runtime اضافه نشود.
- کلید ناموجود fallback فارسی **واقعی** با همان آرگومان و formatter نیاز دارد؛ برگرداندن namespace.key fallback فارسی نیست. عرضه با key خام یا fallback تأییدنشده مجاز نیست.
- [starter فارسی](starter/messages/fa.json)، [عربی](starter/messages/ar.json) و [انگلیسی](starter/messages/en.json) نمونهٔ محدودند؛ ترجمهٔ کامل برنامه نیستند. عنوان قانونی و محتوای عربی نیازمند بازبینی انسانی‌اند.

## روش مهاجرت

1. فهرست کلیدهای مصرف‌شده از TypeScript AST، نگاشت به namespace و ثبت مسیرهای migrated. LocalStrings فعلاً ثابت و فارسی باقی بماند؛ proxy/getter جهانی بر اساس cookie ممنوع.
2. Server Component از getTranslations و client island از useTranslations استفاده کند. type augmentation در types/i18n.ts کلیدها را به schema فارسی محدود کند. هیچ template به client component تبدیل نشود.
3. feature mapperها label دامنهٔ ثابت را به ترجمهٔ module منتقل کنند یا translator خالص تزریق‌شده بگیرند؛ hook React یا UI module از features import نشود.
4. schemaهای Yup در factory با translator ساخته شوند؛ schema singleton متکی به زبان زمان import نباشد. برای تغییر زبان validate مجدد پس از navigation و پیام درست لازم است. YupValidator فقط یک toast ایجاد کند.
5. constants/helperهای موردنیاز ترجمه locale یا translator را صریح بگیرند. این ورودی request-scoped است؛ مقدار آخرین درخواست در global ذخیره نشود.
6. ابتدا SiteHeader/SiteFooter/AppShell، سپس PropertyDetails/PropertyContact/PropertyBooking، جستجو، پروفایل، رزرو، چت، محتوا و مالک. هر دسته با مسیرهای واقعی ممیزی انجام شود.

## toast، API و محتوا

`apiCall` فعلی messages.fa و متن فارسی network/session/server دارد. ترجمهٔ wrapper کافی نیست. پیام‌های **ساخته‌شده در فرانت** به key مشخص تبدیل و در adapter مرورگر با locale فعال ترجمه شوند؛ transport به hook/context UI وابسته نشود. server call هیچ state mutable مرورگر مصرف نکند.

پیام backend فاقد code و ترجمهٔ معتبر همان متن فعلی می‌ماند؛ مترجم ماشینی در runtime یا پنهان‌کردن جزئیات validation با generic message راه‌حل این فاز نیست. contract پیام API باید جدا مستند شود. notify در لایهٔ apiCall و caller دو بار اجرا نشود. `_STRINGS` وقتی تمام مصرف‌ها، schemaها و helperها مهاجرت شدند حذف می‌شود.

محتوای دیتابیس از فایل پیام‌های UI ترجمه نمی‌شود؛ عنوان آگهی، شهر/محله و محتوای CMS از نسخه‌های قابل‌ویرایش ذخیره‌شده استفاده می‌کنند (بخش‌های بالا). متن فاقد ترجمه، توضیحات میزبان و پیام کاربران با bdi/dir=auto نمایش داده شوند. این موارد استثنای مکتوب اسکن‌اند. metadata فقط برای منابع دارای ترجمهٔ واقعی محلی‌سازی شود؛ تغییر openGraph.locale به عربی/انگلیسی بدون ترجمهٔ metadata انجام نشود. hreflang برای URL یکسان ساخته نشود.
